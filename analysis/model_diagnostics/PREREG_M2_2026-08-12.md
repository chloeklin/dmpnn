# Pre-registration — M2 (`hpg_hier_octamer_edges`): topology vs. junction-edge-feature confound

Written **12 August 2026, before any job is submitted.** Nothing below may be edited after the
first result lands. Corrections go in a dated addendum at the bottom.

Rung 4 of `ARCHITECTURE_LADDER_2026-08-12.md`.

---

## 1. Question

Of the octamer's advantage over HPG-hier, how much is the 8-slot topology and how much is the
loss of the 16-d port-pair junction features?

The intended 2×2 (topology × readout) is confounded: every move from the 2-node graph to the
8-slot chain (HPG-hier/arm C → arm D/octamer) simultaneously drops the 17-d junction edge
feature (`hpg_hier.py:265` returns from the octamer branch before the `Stage2Layer` loop that
consumes `batch.stage2_edge_features`). Factors "topology" and "loss of junction features"
cannot be separated on arms C/D alone, however many folds are added.

**M2 is the missing cell: an 8-slot chain that *does* receive the junction edge features.**

```text
HPG-hier (2-node, stoich, +features)
   → M2   (8-slot, mean, +features)     = topology alone
   → armD (8-slot, mean, -features)     = edge features alone
   → octamer (8-slot, attention, -features) = readout alone
```

## 2. Mechanism, stated precisely

M2 extends `OctamerEncoder`/`OctamerPathLayer` (`chemprop/models/hpg_hier.py`) so that, for each
directed path edge between adjacent slots *i*, *i+1* holding monomers *(m_i, m_{i+1})*, the
message MLP receives `[h_src; e]` where `e` is the same 17-d vector (16-d port-pair one-hot +
1-d transition weight) that `Stage2Layer` uses for the `(m_i, m_{i+1})` transition-graph edge.
The vector is obtained by indexing the existing `2×2×17` block already computed by
`TwoStageHPGFeaturizer._stage2_edges` and already carried in every batch as
`batch.stage2_edge_features` (reshaped from its fixed `(0,0),(0,1),(1,0),(1,1)` row order) — no
new featurization is introduced. Message construction matches `Stage2Layer`'s `mode="feature"`
exactly (`message = MLP([h_src; e])`), because `stage2_edge_weight="feature"` is what every
current HPG-hier run uses; M2 is deliberately built to be comparable, not to explore alternative
edge-weighting schemes.

**Readout: M2 uses `stage2_readout="stoich_weighted"`, exactly like arm D.** On an 8-slot chain
the "stoich_weighted" readout resolves inside `HPGHierMPNN` to `OctamerEncoder(readout="mean")`,
because the slot counts already encode composition (`n_A = round(8 · fracA)`) — mean pooling
over positions *is* the stoichiometric readout once the chain is discretized into slots (HANDOFF
§7). M2 and arm D therefore share every architectural choice except the presence of the 17-d
edge feature in the path layers; this is the one step where a reader will suspect two things
changed at once (readout label differs from HPG-hier's "stoich_weighted" in name only, not in
what it computes for arm D/M2), so it is stated explicitly here rather than left implicit.

The parameter difference vs. arm D is exactly the widened first layer of each
`OctamerPathLayer.msg`: `Linear(d_h, d_h)` → `Linear(d_h + d_e, d_h)`, i.e. `d_e · d_h` extra
weights per layer (bias count unchanged). With `d_h=128`, `d_e=17`, `stage2_depth=2`: `17 × 128 ×
2 = 4352` extra parameters. Verified by direct parameter count (§3 below, and
`tests/test_hpg_hier_octamer_edges.py`).

Configuration matches every other HPG-hier arm: `--stage1_pool sum --stage2_depth 2 --stage2_edge
full --octamer_len 8 --n_random_samples 16 --stage2_readout stoich_weighted --batch_size 64
--epochs 100 --patience 15 --min_epochs 1 --frozen_protocol`.

**This is a full pilot, not a subset.** The arms C/D pilot (2 folds × 1 target × 3 seeds) gave
folds that disagreed in direction and could not be read; a pilot is now defined as all 9 folds,
supporting a 9-fold paired sign test (minimum attainable two-sided p = 0.0039). This is roughly
half a full arm (which would also cover IP).

**Do not generate IP or the B split in this batch.**

## 5. Primary quantity and pre-registered readings

**Primary quantity: ΔR² on `all` rows, A split (monomer_heldout), per fold**, three seeds
averaged at the prediction level before the metric is computed once per fold (never
seed-averaging the metric itself; `y_pred`, never `y_pred_final`).

| Outcome | Reading |
| --- | --- |
| M2 ≈ octamer, arm D ≈ octamer | The edge features are irrelevant; **topology did it**. |
| M2 ≫ arm D | The features matter, and the octamer wins *despite* discarding them — the octamer is leaving information on the table; the obvious next model is 8-slot + attention + features. |
| M2 ≈ HPG-hier | The 8-slot topology contributes nothing once features are held constant; **the loss of features is what changed the model**. |
| M2 midway (between HPG-hier and octamer, not close to either) | Topology and features interact; do not attribute the gain to either factor alone. |

The second row is the interesting one: it is the only reading under which the shipped octamer
model is strictly improvable by a straightforward architectural change (add edge features to the
existing 8-slot + attention design).

**M2 ↔ arm D is only readable on folds {0, 4} until arm D is extended to all 9 folds** (see §4).
M2 ↔ HPG-hier and M2 ↔ octamer are readable on all 9 folds immediately.

## 6. Materiality threshold

Derived the same way as the posemb pre-registration (`PREREG_octamer_posemb_2026-08-05.md` §5):
**median per-cell across-seed SD of `delta_r2` for `hpg_hier_octamer` on `all` rows, EA, 9
folds**, from `_regen_v1_results_individual_runs.csv`.

Per-fold across-seed SDs (EA, `hpg_hier_octamer`), sorted:

| rank | fold | delta_r2 SD |
| --- | --- | --- |
| 1 | 2 | 0.004799 |
| 2 | 1 | 0.011755 |
| 3 | 5 | 0.017518 |
| 4 | 7 | 0.017550 |
| **5 (median)** | **8** | **0.019116** |
| 6 | 3 | 0.066683 |
| 7 | 0 | 0.069486 |
| 8 | 4 | 0.481727 |
| 9 | 6 | 0.812454 |

**Materiality threshold = 0.0191** (median of 9 values, odd count, no averaging ambiguity —
avoiding the off-by-one median-convention slip documented in the posemb addendum of
2026-08-11). "Large difference" means a per-fold ΔR² gap exceeding this threshold in magnitude;
"no material difference" means the gap falls within `[-0.0191, +0.0191]`.

Because M2 is a new model, no `hpg_hier_octamer_edges`-specific SD estimate exists yet; using the
octamer's own noise floor as the threshold (as the posemb ablation did) is the only
pre-registerable choice before any M2 data exists.

## 7. Statistical caution

With three seeds per cell, an across-seed SD estimate carries roughly 40% relative error (carried
forward from the K=1 and posemb arms). Any claim about a *change* in stability requires a paired
per-cell sign test across folds (9 folds → minimum two-sided p = 0.0039), not a comparison of two
medians. Pre-committing to that test now, consistent with prior arms.

## 8. Negative controls

1. **Sidecar check.** Every sidecar must show:
   - `resolved_variant.stage2_mode == "octamer_sequence"`
   - `resolved_variant.stage2_readout == "stoich_weighted"` (which resolves internally to mean
     pooling for `stage2_mode="octamer_sequence"` — see §2)
   - `resolved_variant.octamer_edge_features == true`
   - `resolved_config.n_octamer_params` — must equal arm D's octamer-encoder parameter count plus
     exactly `4352` (`17 × 128 × 2`, see §2 and §9.1)
   - `resolved_config.batch_size == 64`, `resolved_config.frozen_protocol == true`
2. **Parameter-count check.** See §9.1: `n_octamer_params` must differ from arm D by exactly 4352
   and match the by-hand arithmetic, not just the printed number.
3. **Path-collision check.** Output paths use the token `__m2` under `predictions/m2/` and
   `checkpoints/m2/`; no file may overwrite an existing prediction.
4. **Cap check.** No run may have `best_epoch` at the 100-epoch cap.
5. **Non-degeneracy check.** M2's forward pass must differ from arm D's on identical inputs
   (`tests/test_hpg_hier_octamer_edges.py::test_m2_differs_from_arm_d_on_forward_pass`) —
   otherwise the edge-feature pathway is silently a no-op and M2 is a duplicate of arm D.

## 9. Verification performed before job generation (§3 of the task spec)

### 9.1 Parameter count, by hand

`OctamerPathLayer.msg` is `nn.Linear(d_in, d_h)` where `d_in = d_h` (arm D, no edge features) or
`d_in = d_h + d_e` (M2). Per layer:

```text
arm D msg params  = d_h * d_h + d_h                    = 128*128 + 128   = 16,512
M2    msg params  = (d_h + d_e) * d_h + d_h             = 145*128 + 128   = 18,688
per-layer diff    = d_e * d_h                                              = 17*128 = 2,176
stage2_depth = 2 layers → total diff                                      = 2,176 * 2 = 4,352
```

Measured directly (`d_h=128`, `stage1_depth=4`, `stage2_depth=2`, matching the training
config):

| model | `octamer_encoder` params | full model params |
| --- | --- | --- |
| arm D (`hpg_hier_octamer`, readout=stoich_weighted) | 133,376 | 390,273 |
| octamer (`hpg_hier_octamer`, readout=attention) | 133,505 | 390,402 |
| **M2** (`hpg_hier_octamer_edges`) | **137,728** | **394,625** |

`137,728 − 133,376 = 4,352` — matches the by-hand arithmetic exactly. `133,505 − 133,376 = 129`
reproduces the documented attention-readout difference (reference point from the task spec),
confirming the arm D and octamer baselines are unaffected by the M2 change.

### 9.2 Edge features reach the layer (non-zero gradient)

`tests/test_hpg_hier_octamer_edges.py::test_edge_features_receive_nonzero_gradient` builds the
`2×2×17` `monomer_pair_features` tensor with `requires_grad_(True)`, runs it through
`OctamerEncoder.forward`, and asserts `monomer_pair_features.grad` is non-`None` and non-zero.
`test_full_model_backward_is_finite_and_octamer_path_layer_weights_get_gradient` additionally
checks that the edge-feature columns of `OctamerPathLayer.msg.weight` (columns `[d_h:]`) receive
non-zero gradient after a full-model backward pass — a silently-ignored input would leave the
whole gradient block at (numerically) exact zero, which is what these tests rule out.

### 9.3 Indexing correctness against `_stage2_edges`

`test_monomer_pair_block_matches_stage2_edges_output` asserts, for a real `ea_ip.csv` polymer,
that `batch.stage2_edge_features.reshape(n_polymers, 2, 2, -1)[0, m_i, m_j]` equals
`TwoStageHPGFeaturizer._stage2_edges(...)`'s own output row for the `(m_i, m_j)` pair, to
`atol=1e-6` — not eyeballed. `test_gather_path_edge_features_indexes_by_source_target_monomer`
independently verifies `OctamerEncoder._gather_path_edge_features` on a synthetic
`monomer_pair_features` tensor with `arange`-valued entries, so every gathered edge feature can be
checked against its exact expected source-index/target-index slice.

### 9.4 M2 differs from arm D on a real forward pass

`test_m2_differs_from_arm_d_on_forward_pass` builds arm D and M2 with parameters synchronized on
every weight the two share, evaluates both on the same real `ea_ip.csv` polymer, and asserts the
outputs are not `allclose`. Passing this test rules out the failure mode where the edge-feature
pathway is wired in but has no numerical effect (e.g. a shape bug that silently broadcasts zeros).

All four checks pass (`tests/test_hpg_hier_octamer_edges.py`, 8/8; existing Phase-1/posemb/junction
smoke tests unaffected, 18/18 pass unchanged).

## 10. What this does not resolve

Position embeddings (factor 2) and sequence sampling (factor 5) are already excluded by prior
arms (`PREREG_octamer_posemb_2026-08-05.md`, `PREREG_octamer_k1_2026-07-30.md`). The
protocol-matching confound (K=16 stochastic sampling vs. a single canonical sequence) is
untouched by this or any prior rung. M2 ↔ arm D is only readable on 2/9 folds until the arm D
pilot is extended to the full 9 (§4); reported results must state this explicitly rather than
imply a completed 9-fold contrast.
