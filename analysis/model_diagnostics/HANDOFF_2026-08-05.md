comparisons made then; it is **no longer true** of the octamer against the properly-configured
baseline.

Handle this carefully rather than eagerly. The p-value floor is a property of the fold count, and
whether these survive multiple-comparison correction depends on how the comparison family is
defined — a decision that should be **pre-specified and written down before quoting any p-value in
the paper**, not chosen after seeing which ones came out low. With Holm across the eight tests in
the table above, p = 0.004 × 8 = 0.032 would still clear 0.05, but that family is a post-hoc
construction and should not be reported as though it were planned.

## 4. The wDMPNN protocol question is closed on the A split

The SI settles it (p. S4): *"No hyperparameter optimization was performed for the D-MPNN and
wD-MPNN models and the validation set was used only for early stopping."* So the chemprop 1.4.0
CLI defaults **are** the paper's configuration. Our runs deviated in exactly three fields:

| field | paper (`polymer-chemprop/chemprop/args.py`) | regen_v1 |
|---|---|---|
| `batch_size` | **50** (`:93`) | 512 |
| `epochs` | **30** (`:382`) | 300 cap |
| early-stop halting | **none exists in v1** | patience 15 |

Everything else matched — hidden size 300, depth 3, dropout 0.0, ReLU, `bias` False, bond
messages, weighted-mean aggregation, `ensemble_size` 1, no gradient clipping, LR 1e-4→1e-3→1e-4
with 2 warmup epochs, and an FFN of `Linear(300→300)→ReLU→Linear(300→1)`. (v1's
`ffn_num_layers=2` and v2's `n_layers=1` build the identical network; the two versions count
layers differently.)

A consequence of the old settings worth recording: patience-15 halted training at a median
`best_epoch` of 48, about 63 of the declared 300 epochs. NoamLR's decay is calibrated to reach
`final_lr` at `total_steps`, so the learning rate stopped at roughly 6.2e-4 and **never annealed**.
The published configuration runs all 30 epochs and anneals fully.

**Result: the baseline got better and the conclusion held.** Group-mean R² rose from 0.970/0.962
to 0.982/0.976 — the properly-configured baseline places chemistries better than HPG-hier does on
IP. Its ΔR² stayed at 0.397/0.565. "The baseline was under-tuned" is closed off.

**Limitation to state, not hide:** the B split was not re-run (compute budget). Protocol parity is
verified on the **A split only**.

One residual difference that is not a hyperparameter: our port is chemprop **2.2.0**, the original
is **1.4.0**, and the atom featurization differs (≈75 features covering atomic numbers 1–36 plus
iodine, versus 133 covering 1–100). Every element in this dataset is representable in both, and all
models compared share the same featurizer, so the comparison is internally fair. Describe it as a
reimplementation using the published hyperparameters, not as the original code.

## 5. Why does the octamer work? — the actual open question

Five factors separate `hpg_hier_octamer` from `hpg_hier`. One is now excluded.

| # | factor | status |
|---|---|---|
| 1 | topology: 2 nodes → 8-slot chain | open |
| 2 | positional embeddings (8 learned vectors) | **open — leading candidate** |
| 3 | readout: stoichiometry-weighted → attention | open |
| 4 | edge features: 17-d present → **absent** | **open — leading candidate** |
| 5 | replicas: 1 → 16, averaged in the loss | **excluded, §6** |

Factor 4 is the strange one and deserves the most thought. `OctamerPathLayer.forward(h, edge_index,
n_nodes)` takes no edge features at all, so the octamer **discards** the 16-d port-pair features
and the transition weight that `hpg_hier` uses. It wins while seeing *less* junction chemistry.
Either that information was not helping, or the explicit sequence more than compensates.

**Note also what the octamer does with composition.** `n_A = round(8 · fracA)` turns the
stoichiometric fraction into slot counts — composition becomes structure rather than a multiplier.
That is a candidate explanation which is not on the five-factor list, because it is a consequence
of factor 1 rather than an independent axis. Worth stating.

**A measured limit on the mechanism.** With `stage2_depth = 2`, a slot exchanges messages with at
most ±2 positions before pooling; slot 0 never sees slot 7. The octamer captures **local blockiness
in a ±2 window**, not global chain arrangement. Any claim about "explicit sequence representation"
should be qualified accordingly, and raising `stage2_depth` for the octamer alone is a cheap future
probe.

## 6. K=1 arm result — factor 5 is excluded

Pre-registered in `PREREG_octamer_k1_2026-07-30.md` before submission. Two post-hoc corrections are
disclosed there as dated addenda.

**Supported outcome: C — neither the primary metric nor stability moves materially.**

| | result |
|---|---|
| primary metric, D folds, random rows | inside the 0.024 pre-registered threshold under all three computable readings |
| seed-SD rise, paired per cell | **5/9** D, **3/8** S, **8/17** overall; exact sign p = 1.00, 0.73, 1.00 |

Two lessons worth carrying:

1. **The pre-registered primary quantity was uncomputable.** ΔR² cannot be evaluated on
   `random`-only rows — `compute_copolymer_metrics` keeps only groups with ≥2 distinct `poly_type`
   values, and a random-only subset leaves one row per group. When pre-registering a subset metric,
   check it is defined on that subset.
2. **The `block`/`alternating` rows are not a pure negative control.** K=1 changes the shared
   trained weights, so predictions move on rows whose forward pass never used replicas.

**Consequence.** The octamer's low seed SD is no longer explained by in-loss ensembling — that was
the standing hypothesis and it did not survive. Both the advantage and the stability are open.

## 7. Compute — the claim is withdrawn

`_WeightedBondMessagePassingMixin.message` rebuilt the atom-to-bond mapping with a Python loop over
a CUDA tensor, one host–device synchronisation per bond, twice per forward pass. HPG models were
never affected — they use `MABBondMessagePassing`, which has no such loop.

| | batch | epochs run | s/epoch | SU/run |
|---|---|---|---|---|
| wDMPNN, original config, vectorised | 50 | 30 | **20.2** | **6.0** |
| wDMPNN, regen_v1, pre-fix | 512 | ~63 | 134.2 | 85.0 |
| HPG-hier | 64 | ~31 | 115.4 | 36.5 |
| HPG-octamer | 64 | ~34 | 119.2 | 41.1 |

The 54-run A-split arm cost 0.33 kSU against a 4.6 kSU projection.

**The "HPG is cheaper" claim reverses** — wDMPNN is now ~6× cheaper per run than HPG-hier. **Do not
publish the inverse either.** HPG runs with `num_workers=0` against wDMPNN's `4`, an unfixed
inefficiency on our side; and only the wDMPNN side has been re-measured post-vectorisation. Report
no cross-family compute comparison until HPG is re-timed with dataloader workers — a few hundred
SU, since per-epoch wall time is low-variance and needs neither multiple seeds nor a full arm.

The one internal comparison that survives: **the octamer costs 13% more than HPG-hier** (41.1 vs
36.5 SU) while building and encoding 16 sequences on 42.9% of rows. Same batch size, same cap, same
LR, neither affected by the defect. If the ensemble were doing useful work this would be a bargain;
per §6 it is not, so it is simply cheap.
